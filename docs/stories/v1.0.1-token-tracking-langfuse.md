# Story v1.0.1 — Token Tracking & LLM Observability

**Version:** v1.0.1  
**Status:** Ready for Development  
**Feature:** Token Usage Tracking per Conversation + Langfuse Integration

---

## User Stories

### Story 1 — Usage Visibility (User-facing)

> **As a** Receipt Pal user,  
> **I want to** see how many tokens my conversations have consumed,  
> **so that** I understand how much AI processing my receipt parsing is using.

**Command:** `/usage`

**Acceptance Criteria:**
- [ ] `/usage` command returns total input tokens, output tokens, and combined total across all of the user's conversations
- [ ] Response is formatted clearly in Telegram (HTML parse mode, consistent with `/stats`)
- [ ] If no conversations exist yet, a friendly "No usage data yet" message is shown
- [ ] `/usage` is listed in `/help` and the welcome message

---

### Story 2 — LLM Observability (Operational)

> **As a** developer operating Receipt Pal,  
> **I want** every Gemini API call to be traced in Langfuse,  
> **so that** I can monitor token usage, latency, cost, and prompt quality from the Langfuse dashboard.

**Acceptance Criteria:**
- [ ] All `chat.completions.create()` calls are captured as traces in Langfuse
- [ ] Each trace carries `session_id=str(conversation.id)` (groups all calls within one conversation)
- [ ] Each trace carries `user_id=str(db_user.id)` (filters by Telegram user in Langfuse dashboard)
- [ ] The same `conversation.id` used as Langfuse `session_id` is the key for `add_token_usage()` — both systems reference the same conversation
- [ ] Traces are named `"receipt-parse"` for discoverability in the dashboard
- [ ] When `LANGFUSE_SECRET_KEY` / `LANGFUSE_PUBLIC_KEY` are not set, the app starts normally without errors (Langfuse is optional)
- [ ] `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_BASE_URL` are documented in `.env.example`

---

### Story 3 — Token Persistence (Data)

> **As a** developer,  
> **I want** token counts stored in the database per conversation,  
> **so that** the `/usage` command can serve accurate data without calling an external API.

**Acceptance Criteria:**
- [ ] `conversations` table has `input_tokens`, `output_tokens`, `total_tokens` columns (INTEGER, NOT NULL, DEFAULT 0)
- [ ] Alembic migration applies cleanly on a fresh and existing database
- [ ] After each Gemini API call, token counts are accumulated (not overwritten) on the conversation row
- [ ] Token counts survive bot restarts (persisted to PostgreSQL)
- [ ] If the Gemini API does not return usage data for a call, the bot logs a warning and continues without error

## Technical Design

### Architecture Changes

```
ReceiptParser.parse(session_id=str(conversation.id), user_id=str(db_user.id))
  │
  ├── Langfuse trace:   session_id = conversation.id (str)
  │                     user_id    = db_user.id (str)
  │                     name       = "receipt-parse"
  │
  ├── stream_options={"include_usage": True} → captures TokenUsage from final chunk
  │
  └── Returns (messages: list[dict], usage: TokenUsage)

photo.py / callbacks.py (callers)
  ├── session_id = str(conversation.id)   ← same value → Langfuse + DB
  ├── user_id    = str(db_user.id)        ← same value → Langfuse (DB uses FK)
  └── add_token_usage(conversation_id=conversation.id, ...)  ← same conversation

/usage command
  └── get_usage_stats(user_id=db_user.id)
      └── SELECT SUM(input_tokens), SUM(output_tokens), SUM(total_tokens)
          FROM conversations WHERE user_id = :user_id
```

### `TokenUsage` Dataclass (new, in `receipt_parser.py`)
```python
@dataclass
class TokenUsage:
    input_tokens: int = 0
    output_tokens: int = 0
    
    @property
    def total_tokens(self) -> int:
        return self.input_tokens + self.output_tokens
```

## Out of Scope (Future)

- Rate limiting or quota enforcement based on token counts
- Cost calculation (token count × price per token)
- Admin dashboard or reporting beyond the Langfuse UI
