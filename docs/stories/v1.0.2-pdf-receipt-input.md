# Story v1.0.2 — PDF Receipt Input

**Version:** v1.0.2  
**Status:** Ready for Development  
**Feature:** Accept PDF files as receipt input and parse them with the existing Gemini AI pipeline

---

## Background

Receipt Pal currently accepts receipt images (photos sent via Telegram). Many receipts — especially from delivery platforms, utilities, and e-commerce orders — arrive as PDF attachments (e.g., email invoices forwarded to the bot). This story extends the input pipeline to accept PDF files natively, leveraging Gemini's built-in multimodal PDF understanding without any conversion step.

**Key insight:** Gemini can process PDFs directly (both digital text and scanned/image-based PDFs) via the same OpenAI-compatible API endpoint, using a base64 data URI with `mime_type: application/pdf`. No rendering or pre-processing is needed.

---

## User Stories

### Story 1 — Send a PDF receipt (User-facing)

> **As a** Receipt Pal user,  
> **I want to** send a PDF file of a receipt or invoice to the bot,  
> **so that** it is parsed and saved just like a photo receipt, without any extra steps.

**Acceptance Criteria:**
- [ ] User sends a PDF file (Telegram document) to the bot and receives a parsed receipt card in response
- [ ] The full parsing flow is identical to the photo flow: Gemini extracts fields → draft card shown → user confirms/edits → saved to DB
- [ ] A "⏳ Parsing your PDF receipt…" acknowledgement is sent immediately after receiving the file (before parsing begins), consistent with photo flow UX
- [ ] If the file is password-protected or corrupted and Gemini cannot extract data, the bot replies with a friendly error: _"I couldn't read that PDF. Is it password-protected or a non-receipt file?"_
- [ ] If the PDF exceeds Telegram's 20 MB bot download limit, the bot replies: _"That PDF is too large to process (max 20 MB). Try sending a compressed version."_
- [ ] The parsed receipt source is set to `paper` (or a more specific value if detectable, e.g. utility bill → `billing_period` is set)

---

### Story 2 — PDF in conversation history (Data)

> **As a** developer,  
> **I want** PDF file IDs stored in the conversation history the same way photo file IDs are stored,  
> **so that** multi-turn edit conversations work correctly for PDF-sourced receipts.

**Acceptance Criteria:**
- [ ] PDF Telegram `file_id` is stored in the `image_file_ids` column of `conversation_messages` (reusing existing schema — no migration needed)
- [ ] PDF bytes are cached in RocksDB (`PhotoStore`) by `file_id`, preventing redundant Telegram downloads on retries
- [ ] Edit flow (`receipt:edit` callback) works correctly for PDF receipts — the conversation history is replayed to Gemini including the PDF content
- [ ] `/history` command correctly lists PDF-sourced receipts alongside photo-sourced receipts

---

### Story 3 — Non-PDF document rejection (UX)

> **As a** Receipt Pal user,  
> **I want** the bot to tell me clearly when I send an unsupported file type,  
> **so that** I know to send a PDF or photo instead.

**Acceptance Criteria:**
- [ ] When a user sends a non-PDF document (`.docx`, `.xlsx`, image file sent as document, etc.), the bot replies: _"I can only process PDF files and photos. Please send your receipt as a PDF or photo."_
- [ ] No parsing attempt is made for unsupported file types
- [ ] Voice messages, stickers, and other non-document/non-photo messages continue to be silently ignored (existing behaviour unchanged)

## Technical Design

### Architecture Overview

```
User sends PDF (Telegram document message)
    │
    ▼
document.py handler
    ├── Filter: F.document.mime_type == "application/pdf"
    ├── Size check: document.file_size > 20MB → reject with error message
    ├── Download: bot.get_file(file_id) → bot.download_file(file_path)
    ├── Cache: PhotoStore.store(file_id, pdf_bytes)
    └── Delegate to _process_receipt(message, pdf_bytes=pdf_bytes, ...)
            │
            ▼ (shared logic extracted from photo.py)
    ReceiptParser.parse(images=[], pdfs=[pdf_bytes], history, ...)
            │
            ▼
    _build_messages()
        └── _encode_media()
                ├── images → {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}
                └── pdfs   → {"type": "image_url", "image_url": {"url": "data:application/pdf;base64,..."}}
                         (same Gemini OpenAI-compatible endpoint; PDF MIME type is natively supported)
            │
            ▼
    Gemini streams response → tool calls dispatched → receipt card shown
    (identical flow to photo receipts)
```

### `_encode_media` (replaces `_encode_images`)

```python
def _encode_media(images: list[bytes], pdfs: list[bytes]) -> list[dict]:
    """Encode images and PDFs as base64 data URLs for the Gemini vision API."""
    parts = []
    for img_bytes in images:
        b64 = base64.b64encode(img_bytes).decode("utf-8")
        parts.append({
            "type": "image_url",
            "image_url": {"url": f"data:image/jpeg;base64,{b64}"},
        })
    for pdf_bytes in pdfs:
        b64 = base64.b64encode(pdf_bytes).decode("utf-8")
        parts.append({
            "type": "image_url",
            "image_url": {"url": f"data:application/pdf;base64,{b64}"},
        })
    return parts
```

> **Note for implementer:** Verify that the Gemini OpenAI-compatible endpoint (`/v1beta/openai/`) accepts `data:application/pdf;base64,...` via the `image_url` content type. If not supported, fall back to the native `google-genai` SDK (`types.Part.from_bytes(data=..., mime_type="application/pdf")`). A quick PoC call before full implementation is recommended.

from aiogram.fsm.context import FSMContext
from aiogram.types import Message

router = Router(name="document")

PDF_MIME_TYPE = "application/pdf"
MAX_PDF_SIZE_BYTES = 20 * 1024 * 1024  # 20 MB (Telegram bot download limit)


@router.message(F.document)

    message: Message,
    state: FSMContext,
    session: AsyncSession,
    bot: Bot,
) -> None:
    doc = message.document

            "I can only process PDF files and photos. "
            "Please send your receipt as a PDF or photo."

When input is a PDF:

## Out of Scope (Future)

- PDFs larger than 20 MB (would require Gemini Files API upload — separate story)
- Multi-receipt PDFs (e.g., a monthly statement with many receipts — treat as one receipt for now)
- Password-protected PDF unlocking
- PDF receipts forwarded from email via Telegram's "Share" feature (same flow, no special handling needed)
- Storing raw PDF bytes in persistent file storage (S3/GCS) for audit trail
